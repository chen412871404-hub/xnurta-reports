★核心结论

现在很多亚马逊团队已经在用 AI 写文案、翻译五点描述、整理竞品信息。这些用法确实有价值，但多数仍停留在"问一句、答一句"的阶段——运营依然要自己下载报表、判断问题、整理建议，再到后台逐项核对。

真正能改变团队效率的，是把 AI 变成一套能持续工作的系统：它按团队定好的标准取数、分析、输出建议、记录经验，人负责审核和拍板。这套系统通常被称为 AI Agent。

对江苏盖亚而言，重点不是再增加一个通用聊天工具，而是让现有的多品牌、多站点广告运营拥有一条稳定的数据通道。经授权范围核验，目前账户覆盖 36 个广告档案，涉及 KROSER、VANKEAN、EMPSIGN 三个品牌，以及美国、加拿大、墨西哥、英国、德国、法国、意大利、西班牙、荷兰、日本、澳大利亚和阿联酋等站点。在这样的规模下，单靠人工切换后台、导出报表和复盘，很难长期保持同一套判断标准。

本材料沿用一套已经跑通的 Agent 落地思路，重点讲清三件事：系统由哪几块组成、盖亚应按什么顺序搭建、SparkX MCP 在其中承担什么作用。

一先把这套系统拆开看

这套系统主要由三个部件组成，缺少任何一个都难以长期稳定运行。

脑

第一块：会判断的大脑

即 ChatGPT、DeepSeek 等大模型，能够读懂数据、进行逻辑推理，并写出结构化分析。

但大模型有一个硬边界：它无法自动知道盖亚各站点昨天花了多少广告费，也不知道某次 ACOS 上升之前谁调过预算或竞价。没有真实数据，它只能依据一般经验作答。

通

第二块：取数据的通道

负责把大模型与真实业务连接起来，涵盖市场与竞品数据、店铺经营数据、广告表现、广告结构和操作记录。

有了通道，AI 才能照着盖亚自己的账户做判断；没有通道，运营仍需手动导表，整套系统最终会退化成一个更贵的聊天工具。

序

第三块：固定的工作流程

大模型擅长回答问题，Agent 负责执行任务，Skill 则把团队的做事顺序固定下来。

以"广告周度优化"为例，老运营通常会先排除数据异常和缺货，再依次查看花费无单词、转化下滑词、广告位变化、预算受限和历史调整。把这套顺序写成 Skill 后，不同运营面对同一份数据，都会按相同标准给出建议。

二第一步：给它一个能跑起来的工作台

过去搭建 Agent 往往需要准备服务器、安装环境、维护依赖。现在使用 workbuddy 这类工作台，可以省掉大部分基础设施工作。运营直接在同一界面发任务、查看结果、上传文件和调用 Skill。

workbuddy 客户端还可以读取电脑上的本地资料，适合与后续要使用的 Obsidian 知识库配合。运营看到的是一个统一工作界面，背后则由不同模型、Skill 和 MCP 协同完成任务。

需要提前确认的一件事如果希望每天定时生成异常清单，需要有稳定运行的客户端或外部定时执行环境。这一点不影响先完成数据接入和人工触发的流程。

这一步的产出：团队拥有一个统一入口，可以直接发出"复盘 KROSER 美国站近 7 天广告异常"这类业务指令。

工作台装好之后，第一次做广告分析就会遇到数据问题：运营要么每次下载报表再上传，要么直接把 SparkX MCP 接上。对盖亚这种 36 个档案的账户规模而言，手工导表不适合作为长期方案。

三第二步：模型怎么选——不追最强，追求合适

亚马逊运营中，有些任务需要强推理，有些只是批量整理。如果全部使用最贵的模型，成本没有必要。

任务类型模型选择原因
广告异常诊断、跨品牌资源分配、复杂策略强推理模型判断错误的成本较高
关键词分类、报表整理、格式转换低成本模型规则明确，适合批量处理
周报初稿、SOP 整理、知识库归档稳定且成本可控的模型量大，结果容易审核

同一套系统可以按任务混用模型：关键判断保证质量，重复处理控制成本。

比模型强弱更影响结果的，是数据是否足够新、范围是否完整。广告数据变化很快——一个词上周还在稳定出单，本周就可能因为价格、库存、竞价或广告位变化而失去转化。如果输入的是三周前的报表，模型算得再准，回答的也是三周前的问题。

因此，模型够用即可，数据接入和分析口径需要优先确定。

四第三步：把运营经验写成 AI 能执行的标准

很多团队觉得 AI 输出不稳定，常见原因并不是模型不够强，而是指令缺少业务边界。"帮我分析一下广告"这样的指令，既无法保证每次都看相同的数据，也无法保证不同运营拿到相同结论。

一条合格的广告分析 Skill，至少要明确以下六方面内容：

  1. 分析对象：包括品牌、站点、产品线、ASIN 和广告活动。
  2. 数据范围：例如最近 7 天、30 天及上一周期。
  3. 判断指标：包括花费、订单、ACOS、转化率、CPC、广告位和预算状态。
  4. 输出分类：包括扩量、降价、否定、观察和需要人工确认。
  5. 不能碰的红线：例如有稳定订单的核心词，不能因为短期波动就直接否定。
  6. 输出格式：包括证据、建议动作、风险和复查日期。

盖亚还需要额外增加两条规则

第一，同一阈值不能直接套用到所有品牌和站点。美国站、德国站、日本站的点击成本、转化率和币种各不相同，KROSER、VANKEAN、EMPSIGN 的产品结构也不同。Skill 应先读取对应品牌和站点的历史基线，再判断异常。

第二，背包、公文包、拉杆电脑包和宠物用品不能放在同一个判断模板里。它们的核心词、客单价、转化周期和季节性不同，至少要按产品线分开设规则。

这一步的产出先完成 2 到 3 个 Skill，建议从"广告周度优化""品牌与站点体检""托管组复盘"开始。

五第四步：搭知识库，让系统记住盖亚自己的经验

亚马逊运营最值钱的内容，往往不是公开教程，而是团队长期积累下来的判断：

  • 哪些背包大词有量，但容易拉高 ACOS；
  • 哪些站点需要更保守的出价和预算边界；
  • 哪些产品临近缺货时不适合继续扩量；
  • 哪些广告位对特定 ASIN 有效，哪些只是抬高 CPC；
  • 某次异常究竟是市场变化，还是账户调整造成的。

建议使用 Obsidian 搭建知识库。它本质上是一组本地 Markdown 文件，团队能直接阅读，Agent 也能按权限读取。前期先由一位负责人维护，内容跑顺之后再接公司网盘或代码仓库同步。

知识库分三层

1

第一层：原始证据

保存每次分析所依据的数据范围、指标快照和必要报表。原始证据只存档、不随意改写，便于日后追溯。

2

第二层：经验沉淀

保存经过复盘确认的规律，例如"VANKEAN 某类精准词在英国站需要多少点击才有判断价值"。

3

第三层：执行标准

保存 Agent 每次执行前必须读取的硬规则，包括目标 ACOS、动作边界、核心词保护、库存红线、审批要求和复查周期。

经验层最容易荒废。建议把"分析结束后生成一条待审核经验"作为 Skill 的最后一步，运营确认后再进入正式知识库，避免把一次偶然波动写成长期规则。

为什么不能只接 ERP 报表

广告报告能说明结果，但不一定说明当前怎么设置，也不能完整解释期间发生了什么。

例如，某条活动本周 ACOS 上升：只看报告，可以看到花费和销售变化；加上结构配置，可以看到当前预算、竞价策略和广告位设置；再加上操作记录，才有机会判断问题是否出现在某次调整之后。

一句话概括报告说明结果，配置说明现状，日志说明过程。

七盖亚的实际情况：重点不是多开功能，而是统一判断

盖亚当前的核心产品以电脑背包、公文包、拉杆电脑包为主，同时存在宠物用品等不同产品线。近 30 天销量较高的 ASIN 中，KROSER、VANKEAN 和 EMPSIGN 的主力款覆盖 15.6 英寸、17.3 英寸和 18.4 英寸电脑包，以及商务、旅行、女性通勤、游戏背包等不同使用场景。

这类账户有三个鲜明特点。

多

品牌和站点多

同一条规则如果直接横跨 36 个档案，很容易把正常的站点差异误判为异常。

大

活动和托管组数量大

当前可见 477 个托管组，其中 250 个处于运行状态，覆盖 613 条活动和 1,147 个商品。

异

主力产品相似但定位不同

电脑背包、公文包和拉杆包共享一部分流量词，也存在明显的场景词差异。

数量本身不等于有效管理，真正要看的是：重点花费是否被覆盖、目标是否合理、动作空间是否一致、调整后是否产生结果。运营也需要持续判断哪些词适合跨款复用，哪些词必须留在单独产品线上。

SparkX MCP 要做的不是替代运营思考，而是先把每天重复的查数、对比、追溯和分层完成，让运营把时间放在目标、边界和最终选择上。

八建议先做的三个场景

三个场景不要同时铺开，建议先把第一个跑通，再扩展到后两个。

场景一

广告周度优化

数据输入最近 30 天和上一周期的广告表现、当前结构、广告位、预算状态和历史调整。
Agent 处理先读取盖亚知识库中的品牌、站点和产品线规则，再把问题分为扩量、降效、浪费、预算受限、结构问题和需观察六类。
输出每条建议包含对象、证据、建议动作、动作边界、风险和复查日期。
人的角色负责审核，未经确认不直接修改账户。
场景二

品牌、站点和产品线体检

每周固定回答以下问题：

  • 哪个品牌在增长，哪个品牌的花费增长快于销售；
  • 哪些国家站点正在改善，哪些站点的效率持续走弱；
  • 哪些主力 ASIN 的流量、转化或广告贡献发生变化；
  • 哪些问题需要广告处理，哪些需要库存、价格或页面团队处理。

这样可以避免只盯总 ACOS——总盘改善时，仍可能有个别品牌或站点的问题被掩盖。

场景三

托管组治理与经验回写

Agent 定期检查运行中、暂停和未启动的托管组，核对目标 ACOS、活动覆盖、商品覆盖、动作空间和近期效果。

需要新增或调整托管组时，先生成候选清单和建议参数，运营审核后再调用执行接口。执行完成后，用操作记录核对是否下发成功，并在约定观察期后复盘结果。

每次复盘只把经过确认的结论写回 Obsidian，例如某个品牌在某站点适合什么目标范围、某类产品在什么条件下不应自动扩量。这样知识库会越来越接近盖亚自己的运营标准。

九三个品牌和多个站点怎么分工

建议把账户管理拆成三层。

1

公司总盘

看总花费、广告销售、订单、ACOS、自然销售占比和各品牌贡献，解决资源分配问题。

2

品牌盘

KROSER、VANKEAN、EMPSIGN 分开看增长、效率、主力产品和托管覆盖，解决品牌目标不同的问题。

3

站点和产品线

美国站体量最大，应重点保障稳定和放量；欧洲、日本、澳大利亚等站点按自己的转化和成本基线判断。背包、公文包、拉杆包和宠物用品分别维护关键词与动作规则。

第二步建 Obsidian 三层知识库，写入现有规则约 1 周Agent 每次执行前能读取对应规则
第三步只跑"广告周度优化"一个场景2 至 3 周连续两周稳定出建议，能追溯证据和历史调整
第四步增加品牌站点体检和托管组治理第二个月起从出建议扩展到小范围、可回滚的执行闭环
第三步最关键一次铺开很多场景，容易让数据口径、规则和审批流程同时失控。先让一个场景真正跑起来，再复制到其他品牌和站点。

是否跑通，建议看四个指标：建议采纳率、误报率、运营处理时间、执行后复查完成率。广告结果还会受到价格、促销、库存、页面和市场竞争影响，因此不把短期 ACOS 变化单独当作 Agent 成败标准。

十一这套自动化对盖亚的价值

  1. 减少重复查数。36 个档案不再依赖运营逐个导表，品牌和站点可以用同一套口径比较。
  2. 统一判断标准。不同运营面对相同问题，都会先读取同一套红线、阈值和审批要求。
  3. 保留调整过程。配置和操作记录可以帮助团队回看某次变化前后发生了什么，减少只靠记忆复盘。
  4. 让托管从"数量管理"转向"结果管理"。不是追求开更多托管组，而是持续检查重点花费覆盖、参数合理性和执行后的真实结果。
  5. 积累盖亚自己的运营知识。公开教程只能告诉团队一般方法，SparkX MCP 与 Obsidian 组合之后，才能把盖亚自己的品牌、站点、产品和历史结果沉淀下来。

十二SparkX MCP 作为主驾驶舱的三工具协同场景

以 KROSER 美国站主力电脑背包 B07MK6J5NT 为例，这套流程并不是三种数据并列使用，而是以 SparkX MCP 为主驾驶舱：卖家精灵和 SIF 负责补充外部市场信号，SparkX MCP 负责判断账户问题、生成动作、承接执行和验证结果。

原因很直接：外部工具能看到竞品和公开流量，但看不到盖亚这条广告当前的预算、竞价、广告位、搜索词花费、托管设置，以及谁在什么时间改过它。没有 SparkX MCP，Agent 最多只能提出猜测，无法形成可执行、可追溯的广告方案。

工具在系统中的位置不可替代的价值
SparkX MCP主数据底座、决策中心和执行回路读取盖亚真实的广告表现、结构、设置和调整记录；把外部信号转成指定活动、指定词、指定预算或托管组的动作；执行后还可复查结果
卖家精灵外部市场参照帮助判断问题是否可能来自价格、评价、产品成熟度或竞品格局，而不是盲目把所有问题归因于广告
SIF外部流量雷达帮助判断词和曝光变化是账户内部投放变化，还是自然位、竞品广告位和市场流量变化造成
1

SparkX MCP 先发现真实的账户问题

每周先由 SparkX MCP 扫描盖亚自己的账户，按品牌、站点、产品线、ASIN、广告活动和托管组分层找出异常。它不只看 ACOS，还会同时看花费、订单、销售、点击、预算、广告位、投放结构和历史操作。

在 2026 年 7 月 31 日至 8 月 29 日，KROSER 美国站该 ASIN 的广告花费约为 13,487.53 美元，广告销售约为 45,632.71 美元，广告订单 910 单，ACOS 约为 29.56%。同期商品总销售约为 59,479.62 美元，总订单 940 单，Sessions 为 16,286。

这组数据先告诉团队一件事：这是一条必须精细管理广告的主力链接。接下来不是泛泛地问"竞品在做什么"，而是从 SparkX MCP 下钻到具体活动、搜索词、广告位和历史调整，找出哪一段花费、哪一类词、哪一次设置变化需要处理。

2

卖家精灵帮助排除产品和竞品因素

当 SparkX MCP 发现转化或效率异常，再用卖家精灵核对外部参照，回答同类产品的价格带、评价门槛、上架成熟度和可比竞品是谁。

本次验收中，卖家精灵返回该产品售价 45.99 美元、评分 4.7、评价量 13,782、FBA 履约、2019 年 2 月上架，Listing 质量得分为 100。它是一条成熟老链接，因此如果 SparkX MCP 发现转化突然走弱，不应先把问题归因为评价不足，而应优先检查价格、促销、搜索词相关性和广告结构。

卖家精灵在这里是校准器，不是广告决策的替代品。它帮助 Agent 少走弯路，最终是否调整以及调整哪一条广告，仍由 SparkX MCP 的账户数据决定。

3

SIF 解释外部流量和关键词环境

在 SparkX MCP 锁定可疑 ASIN、活动或关键词后，再用 SIF 看自然搜索、SP 广告、推荐位和竞品可见曝光的变化，判断账户内的异常是否伴随外部流量变化。

本次 SIF 验收显示，该产品最近三个月整体曝光趋势仍偏弱，但最近一周较前一周回升约 17.3%。最新一周自然搜索曝光约占 75.3%，广告曝光约占 24.7%。过去 13 周的广告曝光占比在约 2.9% 至 64.4% 之间波动，说明单周波动不能直接作为改预算或提价的依据。

SIF 同时显示主变体近 30 天销量处于 500+ 档位。这里的销量是区间值、曝光是相对得分，不等同于盖亚后台的精确访问量和订单。SIF 用来解释外部环境，SparkX MCP 用来确认盖亚账户究竟发生了什么。

4

所有动作都由 SparkX MCP 落到具体对象

SparkX MCP 发现的问题卖家精灵和 SIF 的外部证据最终由 SparkX MCP 完成的判断和动作
某词花费上升、订单下降SIF 显示该词自然和竞品广告曝光没有同步恶化下钻当前竞价、广告位、搜索词和近期操作记录，决定降价、观察或暂停，而不是只凭外部波动处理
活动曝光下降且预算受限SIF 显示产品外部流量保持或回升找出受限活动和对应商品，评估历史转化后提出预算恢复或广告位测试，并设置金额上限
点击增加但转化没跟上卖家精灵显示价格或评价落后，SIF 显示新增曝光来自低相关词精确定位低转化搜索词和产品投放，形成否定、降价或拆分活动建议，同时把页面问题交给对应团队
核心词稳定出单但展示不足SIF 显示该词仍有可见流量，卖家精灵确认竞品强度可承受检查该词当前竞价、广告位和预算，设计小范围提价或广告位测试，明确复查日期
托管组效果分化外部工具说明市场环境没有明显同向恶化用托管组配置和操作日志判断目标 ACOS、活动覆盖或动作空间是否需要调整，避免只按总盘数据扩组或关组
5

SparkX MCP 让建议形成闭环

Agent 输出的不是一句"建议增加广告"，而是一张以 SparkX MCP 对象为单位的清单。每条建议都要落到具体品牌、站点、ASIN、活动、广告组、搜索词或托管组，并写明证据、建议动作、动作边界、风险和复查日期。

运营审核后，先通过 SparkX MCP 的已验收能力调整托管组或配置；执行完成后，再查询操作记录确认实际下发内容。经过约定观察期，SparkX MCP 用同一口径复查花费、订单、销售和 ACOS，SIF 与卖家精灵只在需要判断外部变化时再次介入。

完整闭环SparkX MCP 发现问题、定位对象、提出动作、承接执行、复查结果；卖家精灵负责市场校准，SIF 负责外部流量解释，Obsidian 保存已验证的经验。三者不是平均分工——SparkX MCP 是让 Agent 真正能运营账户的核心。

最后：从"会聊天的 AI"到"按盖亚标准工作的流程"

这套系统带来的不是一个更会聊天的 AI，而是一套能按盖亚标准持续工作的运营流程。

建议先用一个周度广告优化场景完成闭环：数据能自动进来，建议有证据，人工能审核，执行后能复查，经验能写回知识库。这个闭环稳定之后，再扩展到品牌站点体检和托管组治理。
